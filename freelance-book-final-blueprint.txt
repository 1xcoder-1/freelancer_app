4. Important Architecture Decision: Supabase
■ Supabase Decision
Supabase is removed from the core architecture by default. The app will use Clerk for authentication, Neon for PostgreSQL,
R2 for file storage, Upstash for Redis and FastAPI for the backend.
If a specific realtime feature becomes easier or more reliable with Supabase Realtime, Supabase can be added later as a
dedicated realtime service. It should not become a second primary database.
Default:
Clerk → Authentication
Neon → PostgreSQL
FastAPI → Backend
SQLAlchemy → DB access
Upstash Redis → Cache / rate limits / temporary data
R2 → Files
WebSockets → Realtime
Brevo → Email
Inngest → Background workflows

23. Free-First Strategy
■ Infrastructure Allocation Strategy
Do not add every service immediately. Start with the smallest reliable architecture and add infrastructure only when a feature
needs it.
START:
Next.js
FastAPI
Clerk
Neon PostgreSQL
SQLAlchemy
Brevo
R2
ADD WHEN NEEDED:
Upstash Redis
Inngest
Firebase FCM
Sentry
Supabase Realtime for selected realtime needs
Avoid:
Neon + Supabase as two primary databases
Two realtime systems for the same events
Redis for permanent application data

24. Security
• Verify Clerk identity on the backend.
• Apply workspace and role permissions in FastAPI.
• Never trust frontend permissions.
• Validate input with Pydantic.
• Rate-limit sensitive APIs.
• Use secure file authorization and signed URLs.
• Keep AI/API/storage secrets server-side.
• Back up PostgreSQL.
• Add audit logs for sensitive operations.
• Add 2FA and stronger security controls before large-scale production.
